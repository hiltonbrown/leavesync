## Why this matters

CI never runs `bun run build`. It lints, typechecks, migrates, and runs tests,
then stops. Every build failure therefore reaches Vercel unchecked: a broken
import, a Server/Client component boundary violation, a bad `next.config.ts`,
or a route that fails to compile all land in a deployment rather than in a red
check on the pull request.

There is a second, subtler consequence. All three Next.js apps include
`.next/types/**/*.ts` in their `tsconfig.json` `include` array. That directory
is generated by `next build` (and `next dev`) and is git-ignored. On a
developer machine that has run the app at least once the directory exists, so
`bun run typecheck` picks up Next 16's generated route and page validators. In
CI the directory never exists, so those validators are silently absent.

The result is inverted: **the local typecheck is stricter than the CI
typecheck**. A typed-route regression that fails on a developer's machine
passes CI. That is the worst possible arrangement, because the signal people
trust least (their own machine) is the only one that catches the class of
error, and the signal that gates merges does not.

Adding a build step fixes both problems at once, provided it runs *before* the
typecheck so the generated types exist when `tsc` runs.

```typescript
      XERO_TOKEN_ENCRYPTION_KEY: z.string().refine(
        (val) => {

            validateEncryptionKey(val);
```

## Commands you will need

All run from the repo root.

```
bun install                # run first if you hit "Cannot find module '@repo/observability/log'"
bun run build              # Turbo build across all apps and packages
bun run typecheck          # tsc --noEmit across the monorepo
bun run check              # Biome/Ultracite lint (check mode, does not write)
```

> If `bun run typecheck` or `bun run test` fails with
> `Cannot find module '@repo/observability/log'`, that is a stale local
> `node_modules` symlink, not a repository defect. Run `bun install` once and
> retry. CI uses `bun install --frozen-lockfile` and is unaffected.

`bun run build` is slow (several minutes) and writes to `.next/`, which is
git-ignored. That is expected and is the only place this plan writes build
output.

### Step 5: Insert the build step before the typecheck step

In the same file, the current ordering is Lint, then Typecheck. Insert a Build
step **between** them, so the generated `.next/types` exist when `tsc` runs.

Replace:

```yaml
      - name: Lint
        run: bun run check

      - name: Typecheck
        run: bun run typecheck
```

with:

```yaml
      - name: Lint
        run: bun run check

      # Build before typecheck: all three Next.js apps include
      # ".next/types/**/*.ts" in their tsconfig include array, and that
      # directory is generated by next build. Without this step the CI
      # typecheck silently skips Next's generated route validators, making it
      # weaker than a local typecheck.
      - name: Build
        run: bun run build

      - name: Typecheck
        run: bun run typecheck
```

Leave every other step exactly where it is.

**Verify** the ordering is now Lint, Build, Typecheck:

```
grep -n "name: \(Lint\|Build\|Typecheck\)" .github/workflows/ci.yml
```

**Expected**: three lines, in ascending line-number order, reading Lint, then
Build, then Typecheck.

Run the three steps in the new order, from a clean build output, with only the

```

bun run check
bun run build
bun run typecheck
```

**Expected**: all three exit 0.

Note: `rm -rf` here only removes git-ignored build output. Do not remove

### Step 7: Confirm the typecheck is genuinely stronger now

This proves the fix does something rather than just adding minutes to CI.

```
rm -rf apps/app/.next apps/api/.next apps/web/.next
bun run typecheck
```

**Expected**: exits 0, but the run is now typechecking *without* the generated
route types, which is exactly what CI did before this change.

Then:

```
bun run build && bun run typecheck
```

**Expected**: exits 0, now *with* the generated route types included.

Both passing is the normal case on a healthy tree. The point of this step is to
confirm the two runs compile different file sets. Confirm that by checking the
generated directory is present in the second run and absent in the first, using
the `ls` command from Step 2.

If the second run fails while the first passes, you have found a real
pre-existing typed-route regression that CI was hiding. Go to STOP conditions.

  it before typecheck.

## Maintenance notes

- **Ordering is load-bearing.** Anyone who later reorders CI steps, or moves
  the build to a parallel job, reintroduces the weak typecheck. The comment in
  the workflow file explains why; keep it there. In review, treat any change
  that puts Typecheck before Build as a regression.
- **Turbo caching.** The `build` task is cached with `.next/**` as an output.
  On a repeat CI run with an unchanged tree Turbo may restore `.next/` from
  cache rather than rebuild. That still populates `.next/types/`, so the
  typecheck stays correct. If remote caching is added later, verify that
  `.next/types/` survives a cache restore.
- **`apps/docs` has no build script** (it is Mintlify, with only `dev` and
  `lint`). Turbo will skip it. That is correct; do not add one.
- **`apps/email` is dev-preview only** and is not deployed. The root `build`
  script in `package.json` is already `turbo build --filter=!email`, so it is
  excluded from `bun run build` today, not just a future option. Excluding
  `apps/app`, `apps/api` or `apps/web` the same way would not be correct.
- **Related plan**: plan 005 (refresh vulnerable dependency pins) requires a
  successful `bun run build` as its verification gate. Landing this plan first
  means CI enforces that gate on every subsequent dependency bump rather than
  relying on the executor remembering to run it.
